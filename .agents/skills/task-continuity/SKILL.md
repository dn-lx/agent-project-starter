# Task / Branch Continuity

Use this skill before any resumed or concurrent direct commit to `dev`, or after a handoff, model switch or lost chat context.

## Source-of-truth order

When sources disagree, use:

1. current repository source, `dev` history, tests and GitHub Issue/optional PR/check state,
2. active task state from the control plane when available,
3. `docs/CURRENT-HANDOFF.md`,
4. chat/session memory.

Never create or switch branches because a model merely remembers one.

## Open branch is not an active task

An open branch may be stale, abandoned, superseded, generated by automation or owned by another task. Before acting:

1. identify the user outcome or requirement ID,
2. inspect recent `dev` commits and any matching Issue, open PR or temporary branch,
3. compare the task with current `dev`,
4. inspect CI/check results and the recorded next step,
5. resume only when the evidence matches the requested task.

If no active task exists, reserve one modifying writer and work from current `dev`; a feature branch is not required.

## Durable task binding

For non-trivial work, bind one task to the repository, single writer, current `dev` SHA and an Issue when useful:

`task → repository → dev → verified commit`

The default is `branch: "dev"` with `pr: null`. Record status and next step in the machine-readable block in `docs/CURRENT-HANDOFF.md`. A draft PR is **not** required for a development task.

## Resume protocol

Before modifying code after an interruption:

1. read Project Memory and Current Handoff,
2. parse/validate task state,
3. inspect the current `dev` commits and relevant Issue or optional PR/branch,
4. verify the work was not already committed/superseded,
5. compare task evidence with current `dev`,
6. inspect the latest commit SHA and relevant checks,
7. confirm the recorded next step is still valid,
8. continue from verified state or explicitly retire/rebind the task.

Do not repeat completed external writes or identical failed repair loops.

## Writer ownership

Without a central lease service, keep one modifying agent per task and serialize writes to `dev`. Reviewers may read in parallel. Parallel implementers should isolate in separate worktrees and integrate sequentially to `dev` without obligatory PRs.

When the future AI Control Plane provides leases, treat its active lease as the write-ownership record, but still revalidate GitHub state before writing.

## Checkpoints

Update task state after meaningful boundaries:
- writer assigned,
- relevant Issue / optional worktree identified,
- implementation checkpoint committed,
- checks run,
- review finding confirmed,
- repair committed,
- ready to commit,
- blocked/interrupted.

Do not update it for every small edit.

## Completion

Before committing, run applicable checks and inspect the proposed diff. Commit directly to `dev`, verify the final SHA and available CI, record unresolved issues, and reset Current Handoff to idle once acceptance criteria are satisfied. No development PR or merge is required. If an isolated temporary branch was used, clean it up only after verifying its commits reached `dev`. Production remains a separately approved `dev → prod` release.
